# Current Windows read-only regression

14 October 2026; desktop version 1.5.1, amplifier firmware V1.1.9. The user confirmed the amplifier was on, phone iAMP disconnected and MOOER Studio closed. USB metadata showed the amplifier interface; no desktop amp applications were running. No phone setting was changed.

The sequence was an independent DeviceProbe current-state read, the actual desktop Read handler, then a fresh independent DeviceProbe read. Each opened/disposed its own session using the current shared dispatcher. The desktop also read all 80 preset names. No parameter update, preset recall or save command was sent. Discovery by scan and forced disconnect/power-cycle behavior were not tested; connection used the known Bluetooth address.

The explicit development command `--read-diagnostics-preview ADDRESS OUTPUT.png` invokes the normal Read handler and normal local export handlers. It writes diagnostics beside the image, and a validated snapshot only after a successful read. Existing evidence paths are refused before connecting, avoiding confusion with an older result. The exported snapshot's firmware, capture time and all raw bytes are verified against the displayed snapshot. Default startup and `--read-preview` behavior are unchanged.

The hardware evidence helper passed. All three full snapshots matched, including the original selected index **4 / British Lead Solo**, Noise Killer Threshold **25** / Level **50**, and every other opaque field. State SHA-256 is `bc565805361362423342fdd441fac9fdb6b2cdb1b2b55f9617a30fa7f12ed5c5`; detail SHA-256 is `644dee6d3ad07f3e5c2f6ed7670e37220b28d71892b2605763c820b5e19c30ce`. These equal the earlier original baseline. No restoration command was necessary because no values changed.

The production diagnostics recorded one completed connection and its disposal, six started/completed read-only commands (identity, two name ranges, state/detail/state), and zero transfer-status events. There were no parameter, recall or save categories. The actual desktop image showed Read complete, V1.1.9, 80 presets and British Lead Solo. This validates normal connection/read/cleanup and exported instrumentation on the new dispatcher; it does not validate fault paths on hardware or resolve the mobile loop cause.

Private evidence: `analysis/private/version-151-hardware-before.json`, `version-151-hardware-read.png`, its adjacent `.iamp-diagnostics.json` and `.iamp-snapshot.json`, `version-151-hardware-after.json`, and `version-151-hardware-verification.json` (passed=true). Hardware data remains untracked.

Software checks passed: all 116 .NET/five Node tests, zero build warnings/errors, local diagnostics/snapshot export checks and source/package history consistency. A pre-existing output-file check preserved the sentinel file and produced no diagnostics, proving the helper rejected the path before attempting a read. The staged code tested on hardware was promoted to the usual application folder and verified against published executable and Desktop/Transport/Protocol DLLs.

After the Windows check, the user reconnected phone iAMP and reported: "Reconnected — normal effects screen is stable." This confirms the user's observed normal read-to-phone handoff on this build. No new passive phone capture or measured observation duration was recorded, so this is not proof of indefinite stability or absence of every status notification. The phone was left connected; no further hardware action was taken for this documentation update. Broader disconnection, cancellation, sleep/resume, Bluetooth toggle, save/recall handoff and power-cycle acceptance remain open. Do not infer that the earlier mobile transfer-screen problem is fixed.
