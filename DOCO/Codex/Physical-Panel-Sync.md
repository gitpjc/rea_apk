## Captured read race and correction — 1.41.4

A direct read-only monitor using the production F15ReadSession reproduced the failure during a physical 0D→0C change. All state/detail/state requests completed successfully; CurrentPresetReadGuard rejected the differing before/after state. WorkflowQueue then became terminal, and the desktop’s generic polling catch displayed connection lost. This captured case is a snapshot-consistency race, not evidence of a Bluetooth transport disconnect. It provides a concrete explanation for the same reported polling symptom; the earlier unrecorded exception cannot be independently classified.

The guard now identifies inconsistent complete reads with CurrentPresetChangedException. ReadStableAsync restarts the entire state/detail/state read, with at most three attempts and 100 ms settling between attempts, inside the existing serialized workflow. It returns only a complete matching snapshot. Transport errors, timeouts, malformed responses, transfer state and cancellation are not retried. Exhaustion remains terminal and the desktop asks the user to leave controls still and reconnect rather than claiming Bluetooth loss. Mutation preconditions still compare the fresh result with the expected source, and no mutation/save is replayed.

All 60 affected consistency/retry, command-session, workflow and save tests pass. They cover physical-index and same-index changes, mismatched detail, exact retry bounds, cancellation, non-retryable failures and continued workflow availability after a recovered read. Focused real-popup preset-sync UI checks pass; release builds have zero warnings/errors. A scripted save-precondition test was updated to expect the more specific IOException subtype; it still rejects mismatched source data.

The fixed production reader then monitored a physical 0D→0C→0D round trip for 19 successful snapshots without session failure. A fresh independent connection matched every original state/detail byte. No Apply, save, mutation replay or restoration write was sent. This round trip did not itself require an extra read attempt; the retry branch is verified deterministically by scripted tests, while the pre-fix race is captured on hardware. Normal desktop UI acceptance after the fix remains open because computer-use access to the diagnostic host was not approved; a command-line reader is not described as a full desktop UI test. No additional phone stability check was requested.
