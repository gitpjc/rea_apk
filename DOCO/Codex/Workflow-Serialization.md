# Complete workflow serialization

14 October 2026; implemented and read-only hardware-verified in version 1.5.2.

The command dispatcher serializes individual requests. That alone allowed a concurrent API caller to insert commands between a fresh-state check, mutation and readback. `F15ReadSession` now uses `WorkflowQueue` around each public identity/name/current-preset read, supported parameter edit, recall and save. Internal nested reads call private core methods rather than re-entering the non-reentrant queue. Current-preset state/detail/state reads stay together, as do both name ranges and each complete guarded mutation workflow.

Queued cancellation affects only that request. Active failure or cancellation permanently stops later workflows in that session, including validation/readback errors outside the command dispatcher. Reconnection creates fresh queues. Disposal cancels cooperative active and queued operations; an action that ignores cancellation is awaited until it actually finishes, rather than releasing its slot while it continues. The existing command dispatcher still bounds individual transport waits and prevents replay after failure. No command bytes, supported ranges or automatic retries changed.

Eight new offline cases exercise sequence ordering across awaits, queued cancellation, active cancellation, active failure, disposal, uncooperative actions, swallowed cancellation and an illustrative stale second edit. Tests drive the same queue used by Windows; the ordered-command case also uses the real command dispatcher with an in-memory writer. The illustrative edit test changes simulated memory only. It does not validate physical mutation paths.

The user disconnected phone iAMP for read-only hardware verification. DeviceProbe `read-concurrent` on V1.1.9 opened one session, read identity/baseline, then launched current-preset, both name ranges and another current-preset workflow concurrently. Diagnostics show 12 completed read-only commands with complete state/detail/state groups uninterrupted. All three snapshots matched and 80 names loaded. The actual desktop Read handler then completed six read-only commands in a fresh session. Another independent DeviceProbe current read matched all complete original payloads. Both diagnostic connections recorded disposal and zero transfer-status events.

Boundaries remain: serialization is per session, not a global amplifier lock across separate sessions/processes or the phone/panel. Caller-driven compound workflows that span separate public operations are not one transaction. Same-opcode late-reply ambiguity, effect-only external changes, physical fault cases, write regression and the mobile transfer-screen cause remain unresolved. No atomic device transaction or general persistent-write compatibility is claimed.
